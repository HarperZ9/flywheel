# Monitor-outcome source check, 2026-09-23

The first adapter version (commit bf7beffa1) was written from Control Tower's
docs and the BlueDot integration dossier. A source check read Control Tower's
writers at `linuxarena/control-tower@1cc91b7182674a906d4f556c2d2f493c27e51ae9`
(main, committed 2026-09-23T04:36:21Z) and found the adapters wrong on all three
formats. The adapters were rewritten against the writers, and every mismatch
below now has a control in `tests/test_monitor_outcome_shapes.py`. A mutation run
reintroduced 15 of these defects one at a time; the controls caught 15 of 15.

Nothing here was run against a real Control Tower log. Every shape comes from
source and docs at the pinned revision. The formats changed twice in the week
before it (current eval1 Score shape on 2026-09-17, eval2 monitoring on
2026-09-21, both breaking), so a log from another revision may not match.

## Mismatches found, and what the code does now

- CURRENT EVAL1, SCORE KEY. The source writes current eval1 under monitor_<name> (eval_trace_metadata.py:44-46, score_monitors.py:178-187, live.py:78). The key is bare 'monitor' only when the monitor name is empty. The adapter and build_monitor_record default to monitor_scorer='monitor', so a real current-eval1 log reads as ABSENT unless the caller passes monitor_<name>.
- CURRENT EVAL1, WHERE NULL LIVES. The source puts null in the score VALUE, which is an index-keyed mapping ({"0": 3.0, "1": null}). An entry is null when no result exists or when is_unscored(result) holds (monitor_scores.py:85-91). metadata.action_scores holds full Inspect Score dumps and is null only where no result exists, for example a live protocol that never recorded that index (live.py:87-93). The adapter treats value as an opaque summary and takes per-action state only from action_scores. A failed or skipped-by-design action therefore never reads as ABSENT. The dossier's sentence was correct about the mapping. The adapter moved the null into action_scores.
- CURRENT EVAL1, UNSCORED ENTRY. A failed or skipped-by-design monitor score is Score(value=NOANSWER, metadata{monitor_name, error, skipped_by_design, attempts}) (monitor_score.py:73-93). NOANSWER is "N" in inspect-ai 0.3.263 (_metric.py:45). The adapter's _action_entry classifies "N" as UNSUPPORTED, not unscored. CT's own sus_score (monitor_score.py:210-217) also treats a numeric value as no score when metadata.error is set or the value is negative. The adapter would call both of those SCORED.
- CURRENT EVAL1, ENTRY FIELDS. action_scores entries are Score.model_dump(mode='json') objects. They carry value, explanation and metadata, and the monitor name sits at metadata.monitor_name. They have no top-level action, message_id, monitor or draw. _action_entry reads those top-level keys, so action comes out None (the list index i is dropped) and monitor comes out None. The adapter's bare int/float branch matches nothing the source writes.
- CURRENT EVAL1, SAMPLE STATUS. Inspect's Value type admits None only inside a mapping, so CT never writes a top-level null. An action monitor's value is always a mapping. A trajectory monitor's value is a scalar float or "N". The adapter's 'summary is None -> UNSCORED' branch cannot fire on a CT-written log. A failed trajectory monitor (value "N") reads as SCORED, and so does an action mapping whose members are all null.
- ADAPTER DOCSTRING (lines 11-13). The docstring says the importer rejects current eval1 because a skipped score is a top-level null. CT does not write a top-level null: the null is nested in a flat mapping. The pinned importer's _score_value accepts a dict with None members (inspect_evidence_fields.py:51-54 at 91dfd406d). Inference: the importer probably accepts CT-written current-eval1 values, and the rejection came from a fixture shape CT does not produce. The comment at lines 30-31 says 'unscored' marks an action CT 'declined to score'. The source says a monitor 'ran and could not score', which is an error, not a decline.
- LEGACY EVAL1, VALUE SHAPE. A legacy fold's value is a mapping {max, action_<i>, trajectory} (docs Output section; lift_legacy_score in monitor_score.py:104-137). _eval1_legacy expects a number at monitor_<name>.value. Every real legacy fold therefore reads as UNSUPPORTED, and the per-action action_<i> values and the trajectory value are never extracted.
- LEGACY EVAL1, PREFIX COLLISION. Current eval1 also uses monitor_<name>. _eval1_legacy takes every monitor_ key, so a current-eval1 log declared as eval1-legacy reads as UNSUPPORTED actions instead of being rejected. CT tells the two apart by value shape: is_legacy_score means a dict value with any non-digit key (monitor_score.py:96-101).
- LEGACY EVAL1, INDEX ALIGNMENT. Two kinds of fold indexed only monitor-visible actions: folds from the offline writer before b7131cd1d, and folds from live message-fold scorers. Placing them needs per-action policy-private flags (monitor_score.py:110-125). The adapter does not handle this and sets action=None.
- EVAL2, DRAFT ENTRIES. metadata.scores includes drafts that a protocol scored but did not run (defer-to-resample). The value mapping leaves them out, because summary() skips any message_id not in the executed set (monitor.py:374-376, stated in the docs). _eval2 turns every metadata.scores entry into an action and never cross-checks the mapping. It can overcount and put two entries at one action index.
- EVAL2, NON-NUMERIC VALUES. summary() writes 'unscored' into the mapping for any entry whose value is non-numeric or bool (monitor.py:383-387). The entry itself keeps its original value, for example a code monitor's "N". _action_entry marks such entries UNSUPPORTED, while CT's own mapping marks them unscored.
- EVAL2, SAMPLE STATUS. The eval2 value is always a mapping (summary() returns a dict), and it is {} when nothing scored. _eval2 reports SCORED for any non-None summary, including {} and a mapping whose members are all 'unscored'.
- EVAL2, SCORE KEY. Running 'inspect score --action append' on a log that already has a monitor score writes the new pass under 'monitor-1' (docs; eval2.py:52-53). ct run monitor2 merges into 'monitor' instead. The adapter reads a single key, so a monitor-1 pass is missed.
- EVAL2, DROPPED FIELDS. Entries also carry explanation (for an unscored entry this is the error text), prompt and model for a prompt monitor or function for a code monitor, and model_role when one is set (monitor.py:271-297 and 347-358). _action_entry keeps only action, message_id, monitor, draw and value, so the reason an entry is unscored is lost.
- VERSION CHECK. The adapter never checks the declared variant against the log. An eval2 log read with adapter='eval1' and the default key 'monitor' has no action_scores, so it returns status SCORED with the eval2 mapping as summary. A current-eval1 score read with adapter='eval2' is misread the same way. Both break the docstring's promise that an unrecognised shape is reported as unsupported. The source has a header marker for this: eval.task_registry_name == 'control_tower/control_eval2'.
- TEST FIXTURES, EVAL2 (test_monitor_outcome_controls.py:41-56, 154-159). The fixtures use a scalar sample-level value (5.0, 1.0) where the source always writes a name/action mapping. They use draw 0 where the source numbers draws from 1 (monitor.py:231, i + 1). They include an entry value of null, which Inspect's Score type does not admit.
- TEST FIXTURES, EVAL1 (test_monitor_outcome_controls.py:168-175). The fixture uses the key 'monitor', a top-level null value and bare numbers in action_scores. CT writes none of these. The eval1 controls therefore exercise a shape that does not exist upstream.

Fixed in the rewrite: all of the above except the two items that are about the
old test fixtures, which were replaced by `tests/monitor_outcome_shapes.py`
builders that follow the writers. Also corrected: the old claim that the importer
rejects current eval1. Run on all three real shapes, `import_inspect_log` accepts
each and keeps the value; it drops score metadata without reporting it.

## Open unknowns

- No real Control Tower .eval log was inspected, and nothing was run. Every shape here comes from source at 1cc91b7 plus the live docs, with no runtime confirmation.
- Whether Inspect writes anything into sample.scores when a scorer returns None is not verified. live.py's _monitor_verdict_scorer returns None when nothing was recorded.
- The exact field set of Score.model_dump(mode='json') in inspect-ai 0.3.263 (answer, history and so on) was not verified.
- Whether eval1 'ct run monitor' refuses an eval2 log is unknown. A grep of ct_runs/monitor/task.py found no eval2 check, and the function body was not read in full.
- The legacy fold writer itself was not inspected. The fold keys {max, action_<i>, trajectory} come from the docs and CT's reader (lift_legacy_score). The reader ignores any other keys, so other fold keys, if they exist, are unknown.
- The older MonitorResult overlay shape (sus_score and last_error, stored in the trajectory overlay rather than sample scores) is covered by none of the three adapters. Its full layout was not examined.
- Live eval1 protocols also store the scores of discarded proposals in substep message metadata under 'monitor_scores' (MONITOR_VERDICTS_KEY). No adapter reads this. Whether it is in scope is a decision for the operator.
- Inference, not tested: the eval2 entry dict spreads the monitor Score's metadata after action, message_id, value and explanation (monitor.py:350-356). A code monitor whose metadata uses one of those keys would overwrite it.
- summaries.json drops metadata.action_scores once it exceeds 1 KB (docs). A consumer that reads summaries instead of full samples would lose per-action detail. Which input build_monitor_record receives in practice was not traced.
- Formats are moving fast. eval2 monitoring landed 2026-09-21 (#1977, breaking), the current eval1 Score shape on 2026-09-17 (#1822, breaking), and main was pushed at 2026-09-23T06:17Z. Every finding here is pinned to 1cc91b7 and the 06:54-06:59Z UTC page reads.
- Tool limitation: Gather's web adapter hashes extracted text, not raw bytes. Raw-byte sha256 and HTTP status came from curl. GitHub source files and API responses were fetched with curl, not Gather, because Gather's HTML parser would mangle .py text. WebFetch was not used.
- Some commits-by-path API calls did not record an HTTP status or sha256 (marked 'not recorded' in sources_checked).

## Version detection

Primary marker, from the source (SAYS): an eval2 log carries eval.task_registry_name == "control_tower/control_eval2" (eval_logs/eval2_seat.py:23-24). ct run monitor2 refuses any log without it (ct_runs/monitor/eval2.py:46-50). The docs site says only that monitor2 "takes eval2 logs only, since it reads the seat". The header marker is not on the site. Secondary sample-level signals (INFERRED from the writers): eval2 puts one score at key 'monitor', or 'monitor-N' after a direct append. Its value has keys like name/action, name/draw/action or name/trajectory, and it has metadata.scores. Current eval1 uses key monitor_<name>, with either a value mapping whose keys are all digits plus metadata.action_scores, or a scalar value (float or "N") for a trajectory monitor. Legacy eval1 uses key monitor_<name> with a value mapping that has any non-digit key, which is CT's own is_legacy_score test. Current and legacy eval1 scores can sit side by side in one log, because scores accumulate. An eval1 monitor with an empty name is keyed plain 'monitor' and collides with eval2's key, so read the header marker before trusting the key. eval.metadata.derived_from appears on monitored copies of both versions and does not tell them apart.

## Real trace options

No real Control Tower monitor log has been read yet. The options, as found:

Use the CC-BY-4.0 dataset anonymouslinuxarena/linuxarena-public (revision 2fd29f9c7bc190fb873bd76c6bd648f22b9ab0a7). It is the only source found that has both an explicit open license ("Trajectories: CC-BY-4.0.") and real LinuxArena monitor scores. Per action it stores monitor_response.sus_score, per trajectory it stores traj_monitor_response, and it carries main_task_success and side_task_success outcomes. Build one derived, attributed projection from a single monitor-rerun record, for example 'GPT-5 Nano monitor on Haiku attack'. Keep only the monitor scores and outcomes, and scan the record first, because the manifest flags 34 'mongo uri' hits. The format is a Control Tower JSONL export, not an Inspect .eval, so the sidecar needs a small adapter. Getting the record means streaming or range-scanning the 704,485,115-byte sample.jsonl, which needs the user's approval before it is downloaded. Pair it with three other sources. (a) The smallest MIT-licensed straj_linuxarena .eval (126,940 bytes) gives a real native Inspect .eval. I verified that its monitor values are NOT in the Inspect score fields. (b) The MIT Inspect AI test logs give real v2 JSON with no monitor. (c) The MIT Control Tower trajectory JSON test assets have their monitor fields explicitly null, which makes an absent-monitor control. The ideal source is a Control Tower monitor-run .eval on data.linuxarena.ai, for example 34cce47e92e447c49028cd271b12e1af at 8,261,222 bytes. Those files are publicly downloadable but carry no license statement, so they stay unusable until the LinuxArena maintainers state terms.

Decision needed from the operator before any of these is used: the 704 MB
`sample.jsonl` download from the CC-BY-4.0 Hugging Face mirror, and whether
unlicensed data.linuxarena.ai `.eval` files may be read at all. Until then the
demo stays on the synthetic fixture and says so.

## Strongest competing explanation

Strongest competing argument: the 'independently verified outcome' is another instrument with its own false-acceptance rate, so scoring a monitor against it can move the error instead of removing it. Zhu et al., 'Establishing Best Practices for Building Rigorous Agentic Benchmarks' (arXiv 2507.02825, abstract retrieved), report reward-design flaws in agentic benchmarks. SWE-bench Verified has insufficient tests and TAU-bench counts empty responses as successful, which can mis-estimate agent performance by up to 100% in relative terms. The dossier's own sources point the same way from inside. OpenAI estimates about 30% of SWE-Bench Pro tasks are broken, and its human and agent reviewers overlapped on only 74% of flagged categories. METR estimates 6% label error in MALT's unreviewed benign controls and says some sandbagging cannot be seen in transcripts. A second line comes from Greenblatt et al., 'AI Control' (arXiv 2312.06942, abstract retrieved). They evaluate monitors only as parts of protocols tested against a model that tries to subvert them, and they define the harmful outcome as a backdoor the test cases miss. On that view, monitor-versus-label accuracy on natural or benign data measures the wrong quantity, and the unit of evaluation is safety and usefulness at a fixed audit budget. The Control Tower safety-curves page implements that metric. My reading (inferred): neither source argues against recording monitor judgment and outcome as separate fields. Both argue that the separation alone is insufficient. It needs false-success controls on the outcome checker, with a named verifier and label provenance, and it needs adversarial evaluation at a fixed review budget with thresholds fitted on data held apart from the final test. Does not prove: either competing source was read beyond its abstract; claims from their full papers remain unknown.
