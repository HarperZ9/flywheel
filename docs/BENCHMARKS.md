### What those numbers do not show

- **paired-replication.** The model references in these artifacts no longer resolve to anything on a live roster, so the exact weights behind each arm cannot be fetched again from the reference alone. The per-task outcomes are committed and the arithmetic here is reproducible; the generation is not.
- **paired-replication.** One deterministic sample per task per arm. A single sample measures the greedy decode, not the model.
- **paired-replication.** This compares base weights against continued-pretrained weights on general code completion. It is not a measurement of the verification harness, which is the thing this repository is.
- **receipting-cost.** the timings are one machine, one filesystem and one run; an encrypted, networked or virtualised disk answers fsync on its own terms
- **receipting-cost.** a durable write here is one the drive reported flushed, so the figure rests on the drive's report
- **receipting-cost.** it measures the cost of writing the record, and the action worth recording costs whatever it costs on top, so an action that takes a second is barely moved by any figure here
- **receipting-cost.** every action carries the same payload, so hashing runs on warm cache lines and the verifier's resolver is a two-entry map
- **receipting-cost.** the buffered arm is the shipping path with one syscall removed: an attribution of the cost, and a configuration nobody ships

### Scope

- Each mean is a single-repetition reading; no interval at this sample size.
- Cost covers the attempts whose provider stated a cost; cost coverage gives that share, and a role at zero coverage is unmeasured.
- Latency is wall clock on one machine and includes local model load time.
- Quality numbers cover the roles that returned a readable result. A role with none has no quality numbers for this run, and each ungraded attempt carries its reason beside it, so a malformed answer and a missing one stay apart.
- An envelope found inside a refused answer stays refused and ungraded; its presence records that the harness produced an answer, unchecked.
- The graded metrics come from in-tree fixtures and measure each harness against those tasks.
- The run raised before sealing, so nothing ever checked that the source tree still matched the commit these rows name. The attempts each verified their own workspace, which is a narrower claim.

## Gateway overhead

What the gateway adds to one model call on `/v1/messages` and `/v1/responses`:
a median of 1.3 to 2.0 ms with the gateway token and 2.6 to 3.4 ms with a
virtual key, to the end of the reply. Measured 2026-11-14 on one machine, with
one client and a loopback stub in place of the provider. Provider network time
is not in these figures. Record: `docs/benchmarks/gateway-overhead.json`.

| :-- | :-- | :-- | :-- | --: | --: | --: | --: |
| `/v1/messages` | OpenAI-compatible chat | gateway token | plain | 1.56 | 1.54 | 2.3 | 19.6 |
| `/v1/messages` | OpenAI-compatible chat | gateway token | stream | 1.21 | 2.02 | 24.4 | 26.1 |
| `/v1/messages` | Anthropic Messages | gateway token | plain | 1.46 | 1.45 | 25.9 | 26.1 |
| `/v1/messages` | Anthropic Messages | gateway token | stream | 1.20 | 1.76 | 22.2 | 24.7 |
| `/v1/responses` | OpenAI-compatible chat | gateway token | plain | 1.35 | 1.34 | 25.1 | 25.9 |
| `/v1/responses` | OpenAI-compatible chat | gateway token | stream | 1.21 | 2.02 | 21.2 | 22.1 |
| `/v1/messages` | OpenAI-compatible chat | virtual key | plain | 2.64 | 2.61 | 22.6 | 25.9 |
| `/v1/messages` | OpenAI-compatible chat | virtual key | stream | 1.44 | 3.16 | 21.9 | 22.3 |

Every figure is milliseconds over the same request sent straight to the stub.
For a stream, the first byte is the first text delta a client can read.

### How it was measured

The same request goes straight to a loopback stub provider and through a real
gateway HTTP server pointed at that stub, in turns, one request at a time. Each
call opens a new connection, since the gateway closes the connection after a
stream. The stub holds its first byte for 50 ms, then sends one JSON object or
20 text events with no pause, and notes how long it held each request. That
wait is taken out of every sample. The overhead is the median through the
gateway minus the median to the stub, over 30 warm calls after 3 that are
thrown away. The p95 and max columns are the gateway's 95th percentile and
slowest call, less the stub's median. The client is Python's `http.client` and
the clock is `time.perf_counter`.

Machine: 13th Gen Intel(R) Core(TM) i7-13700KF, 24 logical CPUs, 31.8 GB RAM,
Windows 11 (build 10.0.26320), Python 3.12.10.

### The first call

The first call after a gateway starts also loads the modules the gateway
imports on first use. In a fresh process that call took 61.6 to 66.4 ms more
than the stub. It is not in the table.

### Where the time goes

For a plain `/v1/messages` call with a virtual key (2.66 ms over the stub in
that run), the median time inside each step of the gateway:

- key lookup: 0.23 ms
- request body read and JSON parse: 0.01 ms
- limit and allow-list check: 0.02 ms
- upstream choice: 0.02 ms
- reply read into the neutral form: 0.08 ms
- ledger entry, with the debit inside it: 1.03 ms
- receipt: 0.02 ms

The key debit is 0.96 ms of the ledger entry step: a file lock, a read, a write
and a rename. The remaining 1.2 ms is the two HTTP hops: the gateway's server
accepts the connection, starts a thread and parses the request, and the gateway
opens its own connection to the upstream. A call with the gateway token has no
key lookup and no debit.

The p95 column is 2.3 to 27.0 ms. The slow calls are the gateway's own
connection to the upstream. On Windows, Python connects a socket that has a
timeout without blocking and then waits for it. In a separate check on the
measured machine that wait came back about 15 ms late in 62 to 85 of 200
loopback connects, and a blocking connect was never late. The gateway's
upstream connection carries a timeout. The benchmark client connects blocking,
so calls sent to the stub alone stay within 0.5 ms of their own median at the
95th percentile. Whether a connection to a remote provider is late in the same
way was not measured.

### The key list warm-up

After a debit the gateway opens the key list once on a thread of its own
(Windows only). On the measured machine the first open of that file after its
contents change waits about 6 ms, and rewriting the same contents does not show
the wait, which points at real-time file scanning. Before the warm-up that wait
fell on the next call's key check. With the warm-up off, the same run measured
8.87 ms for a plain call and 8.17 ms to the first text of a stream; with it on,
2.61 ms and 1.60 ms. A call that starts within a few milliseconds of the
previous debit still waits. Every check and every debit reads the file as
before.

### What these figures leave out

- The provider's network time and TLS. The stub is on the loopback interface.
- The system credential store. A virtual key's stored value is read from memory here; the real read was not timed.
- The first call's module loading, which is reported apart from the table.
- Concurrency. This is a single client sending one request at a time. Other gateways publish figures at a request rate, and those are not comparable with these because the conditions differ.
- Connection reuse. Every call opens a new connection to the gateway.
- Any hosted provider, and the Gemini upstream format.
- Other machines and operating systems. One Windows machine was measured.
